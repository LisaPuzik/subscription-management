ТЕХНИЧЕСКИЕ ТРЕБОВАНИЯ К BACKEND-СЕРВИСУ УПРАВЛЕНИЯ ПОДПИСКАМИ И АНАЛИЗА РАСХОДОВ


Технологический стек: Python, FastAPI, FastAPI-Users, PostgreSQL

======================================================================
1. НАЗНАЧЕНИЕ И ОБЛАСТЬ ПРИМЕНЕНИЯ
======================================================================

Система предназначена для управления пользовательскими подписками, учета фактических платежей и анализа регулярных и разовых расходов.

Сервис должен предоставлять REST API для регистрации и авторизации пользователей, создания и изменения подписок, фиксации платежей, получения истории расходов и формирования аналитических отчетов.

1.1. Основные возможности

Система должна обеспечивать:
- регистрацию, аутентификацию и управление учетной записью пользователя;
- создание, просмотр, изменение и удаление подписок;
- учет фактически совершенных платежей и возвратов;
- просмотр истории платежей;
- расчет суммарных расходов за выбранный период;
- анализ расходов по категориям;
- формирование динамики расходов по месяцам;
- прогнозирование предстоящих расходов на основе активных подписок.

1.2. Принятые допущения

1. В рамках первой версии система является сервисом учета подписок и расходов. Автоматическое списание денежных средств с банковских карт и интеграция с платежными провайдерами не входят в текущую область разработки.
2. Фактические платежи регистрируются пользователем вручную либо через импорт из внешнего источника в рамках будущего расширения.
3. Все данные о подписках, платежах и категориях принадлежат конкретному пользователю.
4. Основной идентификатор пользователя — email.
5. Аналитические расчеты выполняются в валюте исходных платежей. Суммы в разных валютах не складываются без отдельной конвертации.
6. Даты и время хранятся в UTC, а при формировании отчетов учитывается часовой пояс пользователя.

======================================================================
2. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ
======================================================================

2.1. Регистрация, аутентификация и авторизация

Для реализации управления пользователями должна использоваться библиотека FastAPI-Users.

FR-2.1.1. Регистрация пользователя

Система должна предоставлять API для регистрации нового пользователя по email и паролю.

При регистрации система должна:
- проверить корректность формата email;
- проверить уникальность email;
- проверить пароль на соответствие требованиям безопасности;
- создать учетную запись пользователя;
- сохранить пароль исключительно в виде криптографического хеша;
- установить начальное состояние учетной записи;
- инициировать отправку письма для подтверждения email.

FR-2.1.2. Подтверждение email

Система должна поддерживать подтверждение email посредством одноразового временного токена.

При запросе подтверждения система должна создавать токен, отправлять его пользователю и предоставлять API для проверки токена.

До подтверждения email пользователь не должен иметь доступ к защищенным ресурсам системы, если включено обязательное подтверждение учетной записи.

FR-2.1.3. Аутентификация пользователя

Система должна предоставлять возможность аутентификации пользователя по email и паролю.

После успешной аутентификации система должна выдавать:
- access token для доступа к защищенным API;
- refresh token для получения нового access token.

Предлагаемые параметры:
- срок жизни access token — 15 минут;
- срок жизни refresh token — 30 дней;
- refresh token должен обновляться при каждом успешном использовании;
- использованный refresh token должен становиться недействительным.

Refresh-токены должны храниться в базе данных в виде хеша. Повторное использование ранее отозванного refresh token должно приводить к отзыву соответствующей сессии или семейства токенов.

Стандартная JWT-стратегия FastAPI-Users не предоставляет полноценный механизм refresh-токенов. Для этого необходимо реализовать дополнительный механизм самостоятельно.

FR-2.1.4. Обновление токенов

Система должна предоставлять API для обновления access token при предъявлении действительного refresh token.

При обновлении токенов система должна:
- проверить срок действия refresh token;
- проверить, не был ли он отозван;
- проверить принадлежность токена пользователю;
- выдать новый access token;
- выдать новый refresh token;
- отозвать предыдущий refresh token.

FR-2.1.5. Выход из системы

Система должна предоставлять API выхода пользователя из текущей сессии.

При выходе refresh token должен быть отозван. Access token должен оставаться действительным не дольше своего установленного срока действия, если дополнительно не используется механизм немедленного отзыва access-токенов.

FR-2.1.6. Восстановление пароля

Система должна поддерживать восстановление пароля через email.

Сценарий:
1. Пользователь указывает email.
2. Система генерирует временный токен восстановления.
3. Система отправляет ссылку для восстановления пароля.
4. Пользователь передает токен и новый пароль.
5. Система проверяет токен и обновляет пароль.
6. Активные refresh-сессии пользователя отзываются.

Ответ на запрос восстановления не должен позволять определить, зарегистрирован ли указанный email.

FR-2.1.7. Изменение пароля и email

Система должна предоставлять API изменения пароля и email.

При изменении email система должна отправлять письмо на новый адрес и выполнять подтверждение нового email до завершения изменения.

FR-2.1.8. Получение информации о пользователе

Система должна предоставлять возможность получения и изменения информации текущего пользователя.

В профиле должны храниться:
- идентификатор пользователя;
- email;
- дата регистрации;
- часовой пояс;
- предпочтительная валюта отображения;
- статус учетной записи.

FR-2.1.9. Удаление учетной записи

Система должна предоставлять API для удаления учетной записи пользователя по его запросу.

Удаление должно выполняться с проверкой прав доступа и подтверждением действия.

Должны быть отозваны все активные сессии. Удаление связанных данных должно выполняться согласованно, без возникновения записей, не связанных с существующим пользователем.

2.2. Управление подписками

FR-2.2.1. Создание подписки

Система должна предоставлять API для создания подписки пользователя.

Подписка должна содержать следующие атрибуты:
- id — уникальный идентификатор подписки;
- service_name — название сервиса;
- description — описание подписки, необязательное поле;
- amount — стоимость подписки;
- currency — валюта подписки в формате ISO 4217;
- billing_interval_unit — единица периода: day, week, month, year;
- interval_count — количество единиц периода;
- start_date — дата первого платежа;
- next_payment_date — дата следующего платежа;
- schedule_anchor_date — техническая дата-якорь расписания;
- is_archived — признак архивирования;
- category_id — идентификатор категории;
- status — статус подписки;
- created_at — дата создания записи;
- updated_at — дата последнего изменения.

Примеры периодичности:
- каждые 7 дней: week, 1;
- каждый месяц: month, 1;
- каждые 3 месяца: month, 3;
- каждый год: year, 1.

FR-2.2.2. Просмотр подписок

Система должна предоставлять API получения списка подписок текущего пользователя.

Каждая запись должна содержать информацию о сервисе, стоимости, валюте, периодичности оплаты, категории, статусе и дате следующего платежа.

FR-2.2.3. Получение информации о конкретной подписке

Система должна предоставлять API получения подробной информации о подписке по ее идентификатору.

Пользователь может получить только собственную подписку.

FR-2.2.4. Изменение подписки

Система должна поддерживать изменение атрибутов подписки.

Изменению могут подлежать:
- название сервиса;
- описание;
- стоимость;
- валюта;
- периодичность;
- дата следующего платежа;
- категория;
- статус.

Изменение подписки не должно изменять ранее зарегистрированные платежи.

Для сохранения исторической достоверности информация о совершенном платеже должна хранить данные о сумме, валюте и категории, актуальные на момент совершения операции.

FR-2.2.5. Удаление подписки

Система должна предоставлять API удаления подписки.

Удаление подписки не должно приводить к удалению истории фактических платежей.

Удаление должно выполняться логически или посредством архивирования записи с сохранением связанных финансовых данных.

FR-2.2.6. Статусы подписки

Система должна поддерживать следующие статусы:
- active — подписка активна;
- paused — подписка временно приостановлена;
- cancelled — подписка отменена.

В прогноз включаются только подписки со статусом active.

При переводе подписки в статус paused будущие платежи не должны включаться в прогноз.

При переводе из paused в active система должна восстановить расписание платежей с учетом актуальной даты.

Отмененная подписка не должна генерировать будущие расходы.

FR-2.2.7. Фильтрация и сортировка

API списка подписок должно поддерживать:
- фильтрацию по статусу;
- фильтрацию по категории;
- фильтрацию по диапазону дат следующего платежа;
- поиск по названию сервиса;
- сортировку по названию, стоимости, дате следующего платежа и дате создания;
- пагинацию.

FR-2.2.8. Расчет следующей даты платежа

Система должна рассчитывать следующую дату платежа на основании начальной даты и периодичности подписки.

При расчете месячной периодичности необходимо сохранять исходный день месяца.

Пример: если первоначальная дата платежа — 31 января, следующие даты должны рассчитываться с учетом последнего дня соответствующего месяца: 28 февраля или 29 февраля, а затем 31 марта.

Для годовой периодичности должна корректно обрабатываться високосная дата.

Если пользователь вручную изменяет дату следующего платежа, расписание должно быть пересчитано с учетом новой даты.

2.3. Управление платежами и расходами

FR-2.3.1. Регистрация фактического платежа

Система должна предоставлять API для регистрации фактического платежа пользователя.

Платеж должен содержать:
- id — уникальный идентификатор платежа;
- user_id — идентификатор пользователя;
- subscription_id — идентификатор подписки, необязательное поле;
- amount — сумма платежа;
- currency — валюта платежа;
- payment_type — тип операции: charge или refund;
- status — статус операции;
- occurred_at — дата и время операции;
- billing_period_start — дата оплаченного периода, если платеж связан с подпиской;
- category_id — категория;
- service_name_snapshot — название сервиса на момент платежа;
- category_snapshot — название категории на момент платежа;
- source — источник записи: manual, import, provider;
- created_at — дата создания записи.

В первой версии платеж, добавляемый пользователем вручную, должен регистрироваться как успешно совершенный.

Сумма платежа должна быть положительной. Возвраты должны регистрироваться отдельной операцией.

FR-2.3.2. Привязка платежа к подписке

При регистрации платежа пользователь может указать subscription_id.

Система должна проверить:
- существование указанной подписки;
- принадлежность подписки текущему пользователю;
- соответствие валюты платежа валюте подписки;
- корректность оплачиваемого периода;
- отсутствие дублирующей записи платежа за тот же период.

Если платеж относится к текущему следующему платежному периоду подписки, система должна сдвинуть дату следующего платежа на очередную дату согласно расписанию.

При внесении исторического платежа за уже прошедший период расписание не должно изменяться.

FR-2.3.3. Просмотр платежей

Система должна предоставлять API получения списка фактических платежей пользователя.

Для каждого платежа должна возвращаться информация о сумме, валюте, дате операции, типе операции, подписке и категории.

FR-2.3.4. История платежей

Система должна предоставлять историю платежей за выбранный временной промежуток.

Должны поддерживаться:
- фильтрация по дате начала и окончания;
- фильтрация по подписке;
- фильтрация по категории;
- фильтрация по типу операции;
- фильтрация по валюте;
- сортировка по дате операции;
- пагинация.

FR-2.3.5. Возвраты

Система должна поддерживать регистрацию возврата денежных средств по ранее проведенному платежу.

Возврат должен быть связан с исходным платежом.

Сумма всех зарегистрированных возвратов не должна превышать сумму исходного платежа.

Возврат должен учитываться в аналитике как уменьшение фактических расходов.

FR-2.3.6. Защита истории платежей

Фактические платежи должны рассматриваться как финансовая история.

Обычное изменение подписки не должно изменять ранее зарегистрированные платежи.

Удаление или исправление ошибочных платежей должно выполняться через отдельный механизм корректировки или отмены операции с сохранением аудиторской информации.

2.4. Управление категориями

FR-2.4.1. Система должна предоставлять API получения доступных категорий расходов.

FR-2.4.2. Система должна поддерживать создание, изменение и удаление пользовательских категорий.

Категория должна содержать:
- id;
- название;
- описание;
- цвет для отображения;
- дату создания.

FR-2.4.3. Категория должна принадлежать конкретному пользователю либо быть системной.

Пользователь не должен иметь возможность изменить или удалить категорию другого пользователя.

FR-2.4.4. Удаление категории не должно приводить к потере исторических данных платежей.

2.5. Анализ платежей и расходов

FR-2.5.1. Общая аналитика расходов

Система должна предоставлять API получения суммарной аналитики расходов пользователя за указанный период.

Аналитика должна содержать:
- общую сумму успешных списаний;
- общую сумму возвратов;
- итоговую сумму расходов;
- количество платежей;
- распределение расходов по валютам;
- при необходимости — детализацию по категориям.

В расчет должны включаться только фактически совершенные платежи и возвраты.

Ожидаемые платежи по подпискам не должны учитываться как фактические расходы.

FR-2.5.2. Расчет итоговых расходов

Итоговые расходы рассчитываются по формуле:

Net Expenses = Successful Charges - Successful Refunds

Successful Charges — сумма всех успешно зарегистрированных списаний за период.
Successful Refunds — сумма всех успешно зарегистрированных возвратов за период.

В расчет включаются операции, дата которых попадает в указанный период.

Пример:
- оплата подписки A — 10 EUR;
- оплата подписки B — 20 EUR;
- оплата подписки C — 15 EUR;
- возврат по подписке B — 5 EUR.

Итоговые расходы: 10 + 20 + 15 - 5 = 40 EUR.

Возврат учитывается в том периоде, в котором он фактически зарегистрирован. Исходный платеж остается в истории.

FR-2.5.3. Учет валют

Все расчеты должны выполняться с учетом валюты платежа.

Суммы в EUR, USD и других валютах должны возвращаться отдельными итогами.

Сложение денежных сумм разных валют без конвертации запрещено.

Пример структуры ответа:

{
  "totals_by_currency": [
    {
      "currency": "EUR",
      "gross_charges": "100.00",
      "refunds": "10.00",
      "net_expenses": "90.00"
    },
    {
      "currency": "USD",
      "gross_charges": "50.00",
      "refunds": "0.00",
      "net_expenses": "50.00"
    }
  ]
}

Конвертация валют может быть добавлена отдельным модулем с хранением исторических курсов.

FR-2.5.4. Аналитика по категориям

Система должна предоставлять API распределения расходов по категориям за выбранный период.

Для каждой категории должны возвращаться:
- идентификатор категории;
- название категории;
- сумма успешных списаний;
- сумма возвратов;
- итоговые расходы;
- количество операций;
- валюта.

Расчет выполняется по категории, зафиксированной в момент совершения платежа, а не по текущей категории подписки.

FR-2.5.5. Динамика расходов по месяцам

Система должна предоставлять API получения динамики расходов пользователя по месяцам.

Для каждого месяца должны рассчитываться:
- сумма списаний;
- сумма возвратов;
- итоговые расходы.

Результат должен быть пригоден для построения графиков на стороне frontend.

Если за месяц не было операций, месяц должен присутствовать в результирующем наборе с нулевыми значениями.

Группировка выполняется по локальному календарному месяцу с учетом часового пояса пользователя.

FR-2.5.6. Расчет предстоящих расходов

Система должна предоставлять API прогнозирования расходов на следующий календарный месяц.

Прогноз рассчитывается на основании расписания активных подписок пользователя.

Алгоритм:
1. Определить следующий календарный месяц относительно текущей даты пользователя.
2. Получить все активные подписки пользователя.
3. Исключить подписки со статусами paused и cancelled.
4. Для каждой оставшейся подписки рассчитать даты платежей, попадающие в выбранный месяц.
5. Определить сумму каждого ожидаемого платежа по актуальной стоимости подписки.
6. Сгруппировать ожидаемые платежи по валютам и категориям.
7. Рассчитать итоговую прогнозируемую сумму.

Формула:

Forecast Expenses = сумма сумм всех ожидаемых платежей активных подписок за период.

Для подписки с несколькими датами платежа в выбранном месяце учитывается каждая дата. Это необходимо для подписок с еженедельной или другой частой периодичностью.

Пример:
- Streaming — ежемесячно, 10 EUR, один платеж в месяце;
- Cloud — ежемесячно, 5 EUR, один платеж в месяце;
- Software — ежегодно, 60 EUR, один платеж в выбранном месяце.

Итоговый прогноз в этом примере составляет 75 EUR.

Если дата годового платежа не попадает в выбранный месяц, годовая подписка в прогноз не включается.

Прогноз не является фактом совершения платежа и должен возвращаться отдельно от аналитики фактических расходов.

FR-2.5.7. Детализация прогноза

API прогноза должно возвращать:
- общий прогноз по каждой валюте;
- перечень подписок, включенных в прогноз;
- название сервиса;
- сумму платежа;
- ожидаемую дату;
- категорию;
- периодичность.

FR-2.5.8. Кэширование аналитики

Система может использовать кэширование результатов аналитических запросов.

При изменении подписки, создании платежа, регистрации возврата или изменении категории соответствующие кэшированные значения должны инвалидироваться.

Тяжелые вычисления могут выполняться асинхронно без блокировки основных CRUD-операций.

2.6. Дополнительные требования к API

FR-2.6.1. Все API должны возвращать данные в формате JSON.

FR-2.6.2. API должны иметь единую структуру ответов и ошибок.

FR-2.6.3. Все endpoint-ы, кроме публичных endpoint-ов регистрации и аутентификации, должны требовать действительную авторизацию.

FR-2.6.4. Для списковых endpoint-ов должны поддерживаться пагинация, фильтрация и сортировка.

FR-2.6.5. Должна обеспечиваться автоматическая генерация OpenAPI-документации.

3. ДОКУМЕНТАЦИЯ API

3.1. Общие положения

ВАЖНО: раздел 3 сохранен как историческое описание API и не является нормативным источником контрактов. Актуальные методы, схемы запросов и ответов, обязательность заголовков и правила обработки определяются разделами 7 и 8. При любом расхождении применяются разделы 7 и 8.

Базовый URL: /api/v1

Формат данных: application/json.

Для защищенных endpoint-ов используется заголовок:
Authorization: Bearer <access_token>

Для операций создания подписок и платежей рекомендуется использовать заголовок:
Idempotency-Key: <unique-key>

3.1.1. Формат ошибок

Все ошибки должны возвращаться в едином формате:

{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid subscription amount",
    "details": {
      "field": "amount"
    },
    "request_id": "uuid"
  }
}

Основные HTTP-коды:
- 200 — успешное выполнение запроса;
- 201 — запись успешно создана;
- 202 — запрос принят в обработку;
- 204 — операция выполнена, тело ответа отсутствует;
- 400 — некорректный запрос или недопустимая операция;
- 401 — пользователь не авторизован;
- 403 — недостаточно прав;
- 404 — ресурс не найден;
- 409 — конфликт данных или повторная операция;
- 422 — ошибка валидации входных данных;
- 429 — превышено ограничение частоты запросов;
- 500 — внутренняя ошибка сервера.

Для ресурсов, принадлежащих другим пользователям, рекомендуется возвращать 404, чтобы не раскрывать факт существования чужой записи.

3.2. API регистрации и авторизации

Реализация стандартных операций выполняется через FastAPI-Users. Префиксы маршрутов должны быть зафиксированы в конфигурации приложения.

- POST /auth/register — регистрация пользователя;
- POST /auth/jwt/login — авторизация пользователя;
- POST /auth/jwt/logout — выход из системы;
- POST /auth/refresh — обновление токенов;
- POST /auth/forgot-password — запрос восстановления пароля;
- POST /auth/reset-password — сброс пароля;
- POST /auth/request-verify-token — запрос подтверждения email;
- POST /auth/verify — подтверждение email;
- GET /users/me — получение профиля;
- PATCH /users/me — изменение профиля;
- POST /users/me/email-change — запрос изменения email;
- POST /auth/confirm-email-change — подтверждение нового email;
- DELETE /users/me — удаление учетной записи.

POST /auth/register

Создание пользователя.

Тело запроса:

{
  "email": "user@example.com",
  "password": "StrongPassword123!"
}

Успешный ответ — 201 Created:

{
  "id": "uuid",
  "email": "user@example.com",
  "is_active": true,
  "is_verified": false
}

POST /auth/jwt/login

Авторизация. Метод FastAPI-Users принимает данные в формате application/x-www-form-urlencoded.

Параметры:
- username — string, email пользователя;
- password — string, пароль.

Поле username является именем поля OAuth2-формы, а не отдельным пользовательским логином.

Успешный ответ должен содержать access token и данные токена обновления согласно выбранной реализации.

POST /auth/refresh

Пользователь передает refresh token в соответствии с принятой схемой хранения токенов.

Успешный ответ:

{
  "access_token": "new_access_token",
  "token_type": "bearer",
  "expires_in": 900
}

Новый refresh token должен выдаваться и передаваться безопасным способом. Для браузерного клиента рекомендуется использовать cookie с атрибутами HttpOnly, Secure и подходящим SameSite, с CSRF-защитой.

POST /auth/forgot-password

Запрос восстановления пароля.

Тело запроса:

{
  "email": "user@example.com"
}

Ответ: 202 Accepted.

POST /auth/reset-password

Сброс пароля.

Тело запроса:

{
  "token": "reset_token",
  "password": "NewStrongPassword123!"
}

Ответ: 200 OK.

GET /users/me

Получение информации о текущем пользователе.

Пример ответа:

{
  "id": "uuid",
  "email": "user@example.com",
  "timezone": "Europe/Vilnius",
  "preferred_currency": "EUR",
  "created_at": "2026-11-01T10:00:00Z"
}

DELETE /users/me

Удаление учетной записи пользователя. Требует аутентификации и дополнительной проверки подтверждения операции.

Пример тела запроса:

{

Ответ: 201 Created.

{
  "id": "uuid",
  "service_name": "Netflix",
  "amount": "15.99",
  "currency": "EUR",
  "billing_interval_unit": "month",
  "interval_count": 1,

GET /subscriptions

Поддерживаемые query-параметры:

- due_from — date, начало диапазона платежей;
- due_to — date, конец диапазона платежей;
- search — string, поиск по названию;
- sort_by — string, поле сортировки;
- sort_order — string, asc или desc;

Пример:

Ответ:

{

Изменение параметров подписки.

Ответ: 200 OK.

DELETE /subscriptions/{subscription_id}

Логическое удаление или архивирование подписки. Ответ: 204 No Content. История ранее совершенных платежей сохраняется.

3.4. API управления платежами

- POST /payments — регистрация платежа;
- GET /payments — получение истории платежей;
- GET /payments/{payment_id} — получение конкретного платежа;
- POST /payments/{payment_id}/refunds — регистрация возврата.

POST /payments

Пример тела:

{
  "subscription_id": "uuid",

  "occurred_at": "2026-11-15T09:30:00+02:00",

При успешном создании система должна:
- проверить принадлежность подписки пользователю;
- проверить валюту;
- проверить дату и оплачиваемый период;
- проверить отсутствие дублирующего платежа за этот период;
- создать запись фактического платежа;
- при необходимости обновить дату следующего платежа подписки.

Ответ: 201 Created.

{
  "id": "uuid",

  "payment_type": "charge",
  "status": "succeeded",
  "occurred_at": "2026-11-15T07:30:00Z"
}

GET /payments

Поддерживаемые параметры:
- date_from — date, начало периода;
- date_to — date, конец периода;
- subscription_id — UUID, фильтр по подписке;
- category_id — UUID, фильтр по категории;
- currency — string, валюта;
- payment_type — string, charge или refund;
- sort_order — string, asc или desc;
- limit — integer, количество записей;
- offset — integer, смещение.

Пример:
GET /api/v1/payments?date_from=2026-11-01&date_to=2026-12-01&currency=EUR&limit=20

Ответ:

{
  "items": [
    {
      "id": "uuid",
      "subscription_id": "uuid",
      "service_name": "Netflix",
      "amount": "15.99",
      "currency": "EUR",
      "payment_type": "charge",
      "status": "succeeded",
      "occurred_at": "2026-11-15T07:30:00Z"
    }
  ],
  "pagination": {
    "total": 1,
    "limit": 20,
    "offset": 0
  }
}

POST /payments/{payment_id}/refunds

Регистрация возврата.

Пример тела:

{
  "amount": "5.00",
  "occurred_at": "2026-11-20T12:00:00Z"
}

Система должна проверить, что:
- исходный платеж существует;
- платеж принадлежит пользователю;
- сумма возврата положительна;
- суммарная величина возвратов не превышает сумму платежа.

Ответ: 201 Created. Возврат создается как отдельная запись с типом refund.

4. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

4.1. Производительность и масштабируемость

NFR-4.1.1. Архитектура backend должна допускать увеличение производительности за счёт добавления экземпляров приложения без изменения бизнес-логики.

NFR-4.1.2. Целевое время ответа системы при штатной нагрузке:
- CRUD-операции — не более 300 мс для 95-го перцентиля;
- аналитические запросы — не более 1 секунды для 95-го перцентиля.

Показатели уточняются по результатам нагрузочного тестирования.

NFR-4.1.3. Основные операции создания, изменения и удаления подписок и платежей не должны блокироваться длительными аналитическими вычислениями.

NFR-4.1.4. Для списковых API должна быть обязательна пагинация с ограничением максимального количества возвращаемых записей.

4.2. Безопасность

NFR-4.2.1. Весь внешний API должен работать исключительно по HTTPS/TLS.

NFR-4.2.2. Пароли должны храниться только в виде криптографически стойких хешей с использованием специализированных алгоритмов хеширования паролей (например, Argon2id или bcrypt).

NFR-4.2.3. Access token и refresh token должны передаваться по защищённым каналам связи и храниться способом, исключающим их несанкционированное использование.

NFR-4.2.4. Система должна проверять принадлежность каждого ресурса текущему пользователю. Проверка должна выполняться на backend-уровне.

NFR-4.2.5. Система должна применять ограничение частоты запросов, прежде всего для регистрации, авторизации и восстановления пароля.

NFR-4.2.6. Все входные данные должны проходить валидацию на стороне backend.

NFR-4.2.7. Система должна использовать параметризованные SQL-запросы или ORM для защиты от SQL-инъекций.

NFR-4.2.8. Система должна обеспечивать защиту от повторного использования одноразовых токенов.

NFR-4.2.9. Повторная отправка запроса на проведение одного и того же платежа с одинаковым ключом идемпотентности не должна приводить к повторному списанию средств.

NFR-4.2.10. Секреты, пароли, токены и конфиденциальная информация не должны попадать в логи.

NFR-4.2.11. При использовании cookie для аутентификации должна быть реализована защита от CSRF-атак.

4.3. Совместимость и сопровождаемость

NFR-4.3.1. API должно поддерживать версионирование через URL (например, /api/v1). Изменения, нарушающие обратную совместимость, должны выпускаться в новой версии API.

NFR-4.3.2. Конфигурации окружений development, test и production должны храниться отдельно от исходного кода.

NFR-4.3.3. Проект должен сопровождаться автоматизированными тестами, проверяющими основную бизнес-логику и работу API.

NFR-4.3.4. Миграции структуры базы данных должны выполняться контролируемо с использованием инструмента миграций.

NFR-4.3.5. Версии внешних библиотек должны фиксироваться и регулярно проверяться на наличие известных уязвимостей.

5.1. Корректность

QR-5.1.1. Денежные суммы должны храниться и обрабатываться с использованием точных десятичных типов данных, например DECIMAL/NUMERIC. Использование float для финансовых операций запрещено. Для денежных значений должна учитываться допустимая точность конкретной валюты.

QR-5.1.2. Все алгоритмы расчёта сумм, возвратов, фактических и прогнозируемых расходов должны быть детерминированными и использовать единые бизнес-правила для одинаковых входных данных.

QR-5.1.3. Дата и время должны обрабатываться с учетом часового пояса пользователя.

QR-5.1.4. Операции с финансовыми данными должны выполняться атомарно с использованием транзакций базы данных.

QR-5.1.5. При изменении стоимости или категории подписки исторические данные платежей не должны изменяться.

5.2. Целостность данных

QR-5.2.1. Каждый платеж должен быть связан с существующим пользователем. При наличии связи с подпиской система должна проверять, что указанная подписка принадлежит тому же пользователю.

QR-5.2.2. Удаление подписки не должно приводить к удалению истории платежей.

QR-5.2.3. Удаление пользователя не должно создавать осиротевшие записи.

QR-5.2.4. Уникальность email и ссылочная целостность должны контролироваться ограничениями на уровне базы данных.

QR-5.2.5. Для повторных запросов создания платежа и подписки должна применяться идемпотентность.

QR-5.2.6. Суммарная сумма возвратов по одному платежу не должна превышать первоначальную сумму этого платежа.

5.3. Тестируемость

QR-5.3.1. Бизнес-логика должна быть отделена от инфраструктурного кода.

QR-5.3.2. Unit-тестами должны быть покрыты:
- расчет дат подписок;
- расчет периодичности платежей;
- учет возвратов;
- суммирование фактических расходов;
- группировка платежей по месяцам;
- расчет будущих расходов;
- проверка прав доступа.

QR-5.3.3. Integration-тестами должны проверяться:
- взаимодействие с базой данных;
- транзакции;
- ограничения уникальности;
- обновление токенов;
- обработка конкурентных запросов;
- целостность связанных записей.

QR-5.3.4. Для проверки API-контрактов должны выполняться автоматические API-тесты.

QR-5.3.5. Позитивные, негативные и граничные сценарии должны быть покрыты автоматическими тестами.

5.4. Качество и безопасность кода

QR-5.4.1. Код должен проходить статический анализ.

QR-5.4.2. Изменения кода должны проходить автоматические проверки до включения в основную ветку проекта.

======================================================================
6. СУЩНОСТИ БАЗЫ ДАННЫХ И СВЯЗИ МЕЖДУ НИМИ
======================================================================

Для хранения данных система должна использовать реляционную базу данных PostgreSQL. Каждая сущность должна иметь первичный ключ id типа UUID, если для сущности отдельно не установлено иное. Внешние ключи должны обеспечивать ссылочную целостность.

6.1. User — пользователь

Сущность User должна хранить учетную запись пользователя и поля, необходимые FastAPI-Users.

Обязательные поля:
- id — UUID, первичный ключ;
- email — строка, уникальное значение, обязательное поле;
- pending_email — нормализованный новый email, ожидающий подтверждения, допускается NULL;
- pending_email_reserved_until — дата и время окончания резервации pending_email, допускается NULL;
- hashed_password — строка, хеш пароля;
- is_active — boolean, признак активности учетной записи;
- is_verified — boolean, признак подтверждения email;
- is_superuser — boolean, признак административной учетной записи;
- timezone — строка, часовой пояс пользователя;
- preferred_currency — строка длиной 3 символа, валюта отображения в формате ISO 4217;
- created_at — дата и время создания записи;
- updated_at — дата и время последнего изменения.

Email должен иметь уникальное ограничение на уровне базы данных. Для pending_email создается частичный уникальный индекс по lower(pending_email) для записей, где pending_email IS NOT NULL. Истекшие резервации очищаются фоновым процессом; до очистки адрес остается занятым, что исключает гонки регистрации и смены email. Одновременно приложение в транзакции проверяет отсутствие конфликта между email и активными pending_email разных пользователей. После подтверждения, истечения или отмены смены адреса оба pending-поля очищаются. Пароль в открытом виде хранить запрещено.

Связи:
- один User связан с нулем или несколькими Subscription;
- один User связан с нулем или несколькими Payment;
- один User связан с нулем или несколькими Category;
- один User связан с нулем или несколькими AuthSession;
- один User связан с нулем или несколькими IdempotencyKey;
- один User связан с нулем или несколькими AuditLog.

6.2. Subscription — подписка

Сущность Subscription должна хранить параметры регулярной подписки пользователя и расписание следующих платежей.

Обязательные поля:
- id — UUID, первичный ключ;
- user_id — UUID, внешний ключ на User.id, обязательное поле;
- category_id — UUID, внешний ключ на Category.id, обязательное поле, если категория назначена;
- service_name — строка, название сервиса;
- description — текст, необязательное описание;
- amount — NUMERIC, положительная стоимость подписки;
- currency — строка длиной 3 символа, код валюты ISO 4217;
- billing_interval_unit — перечисление: day, week, month, year;
- interval_count — положительное целое число, количество единиц периода;
- start_date — дата первого платежа;
- next_payment_date — дата следующего ожидаемого платежа;
- status — перечисление: active, paused, cancelled;
- is_archived — boolean, признак архивирования;
- created_at — дата и время создания;
- updated_at — дата и время изменения.

Связи:
- каждая Subscription принадлежит ровно одному User;
- каждая Subscription может быть связана с одной Category;
- одна Subscription может иметь ноль или несколько Payment.

Ограничения:
- user_id обязателен и ссылается на существующего пользователя;
- категория, указанная в category_id, должна быть системной либо принадлежать тому же пользователю, которому принадлежит подписка;
- amount должен быть больше нуля;
- interval_count должен быть больше нуля;
- валюта должна соответствовать формату ISO 4217;
- удаление Subscription не должно каскадно удалять связанные Payment;
- удаление подписки должно выполняться через is_archived=true либо изменение статуса, а не физическое удаление записи, если у нее имеются платежи.

6.3. Payment — финансовая операция

Сущность Payment должна хранить фактически зарегистрированные списания и возвраты. Записи Payment являются источником данных для расчета фактических расходов.

Обязательные поля:
- id — UUID, первичный ключ;
- user_id — UUID, внешний ключ на User.id, обязательное поле;
- subscription_id — UUID, внешний ключ на Subscription.id, необязательное поле;
- original_payment_id — UUID, внешний ключ на Payment.id, необязательное поле; заполняется для операции возврата и указывает на исходное списание;
- category_id — UUID, внешний ключ на Category.id, необязательное поле;
- amount — NUMERIC, положительная сумма операции;
- currency — строка длиной 3 символа, код валюты ISO 4217;
- payment_type — перечисление: charge, refund;
- status — перечисление: succeeded, pending, failed, reversed;
- occurred_at — дата и время фактической операции;
- billing_period_start — дата начала оплаченного периода, необязательное поле;
- service_name_snapshot — строка, название сервиса на момент операции;
- category_snapshot — строка, название категории на момент операции;
- source — перечисление: manual, import, provider;
- created_at — дата и время создания записи;
- updated_at — дата и время последнего изменения записи.

Связи:
- каждая Payment принадлежит ровно одному User;
- Payment может быть связана с одной Subscription;
- Payment может быть связана с одной Category;
- Payment с payment_type=refund должна ссылаться через original_payment_id на исходную Payment с payment_type=charge;
- одна исходная Payment может иметь несколько связанных операций возврата.

Ограничения:
- user_id обязателен;
- если указан subscription_id, подписка должна принадлежать тому же пользователю, что и платеж;
- если указан category_id, категория должна быть системной либо принадлежать тому же пользователю;
- сумма amount должна быть больше нуля;
- валюта платежа должна совпадать с валютой подписки, если платеж связан с подпиской;
- возврат должен иметь ту же валюту, что и исходный платеж;
- сумма всех успешных возвратов по исходному платежу не должна превышать сумму исходного платежа;
- возврат не может ссылаться на другую операцию возврата;
- платежи и возвраты нельзя физически удалять обычными CRUD-операциями;
- для исправления ошибочной записи должна создаваться корректирующая операция либо изменяться статус с сохранением аудиторской записи.

Для сохранения истории в Payment должны храниться снимки названия сервиса и категории. Изменение или удаление подписки и категории не должно изменять эти снимки.

6.4. Category — категория расходов

Сущность Category должна хранить системные и пользовательские категории.

Обязательные поля:
- id — UUID, первичный ключ;
- user_id — UUID, внешний ключ на User.id, допускается NULL только для системной категории;
- name — строка, название категории;
- description — текст, необязательное описание;
- color — строка, цвет для отображения в формате HEX;
- is_system — boolean, признак системной категории;
- is_active — boolean, признак доступности категории;
- created_at — дата и время создания;
- updated_at — дата и время изменения.

Связи:
- пользовательская Category принадлежит ровно одному User;
- системная Category не принадлежит конкретному User;
- одна Category может быть связана с несколькими Subscription;
- одна Category может быть связана с несколькими Payment.

Ограничения:
- пользователь не может изменять или удалять категорию другого пользователя;
- системные категории не могут изменяться или удаляться обычными пользовательскими операциями;
- при деактивации или удалении категории исторические Payment должны сохранять category_snapshot;
- физическое удаление категории, на которую ссылаются подписки или платежи, запрещено; категория должна деактивироваться либо связи должны быть обработаны отдельной операцией;
- для пользовательских категорий следует обеспечить уникальность названия в пределах одного пользователя.

6.5. AuthSession — сессия аутентификации и refresh-токен

Сущность AuthSession должна хранить серверное состояние refresh-сессии пользователя, необходимое для ротации и отзыва токенов.

Обязательные поля:
- id — UUID, первичный ключ;
- user_id — UUID, внешний ключ на User.id;
- refresh_token_hash — строка, хеш refresh token;
- token_family_id — UUID, идентификатор семейства токенов;
- expires_at — дата и время истечения срока действия;
- created_at — дата и время создания сессии;
- revoked_at — дата и время отзыва, допускается NULL;
- replaced_by_session_id — UUID, ссылка на новую сессию после ротации, допускается NULL;
- user_agent — строка, необязательная информация о клиенте;
- ip_address — IP-адрес клиента, если его хранение предусмотрено политикой конфиденциальности.

Связи:
- каждая AuthSession принадлежит ровно одному User;
- один User может иметь несколько AuthSession;
- AuthSession может ссылаться на другую AuthSession, которая заменила ее при ротации токена.

Ограничения:
- refresh_token_hash должен быть уникальным;
- при ротации старый токен отзывается, а новая сессия сохраняется в той же транзакции;
- повторное использование отозванного токена должно приводить к отзыву соответствующего token_family_id;
- все сессии пользователя должны отзываться при сбросе пароля или удалении учетной записи.

6.6. IdempotencyKey — ключ идемпотентности

Сущность IdempotencyKey должна обеспечивать защиту от повторного выполнения запросов создания подписок, платежей и возвратов.

Обязательные поля:
- id — UUID, первичный ключ;
- user_id — UUID, внешний ключ на User.id;
- key — строка, значение ключа идемпотентности;
- request_hash — строка, контрольная сумма тела запроса;
- operation — строка или перечисление, тип операции и endpoint;
- response_status — целое число, HTTP-код исходного успешного ответа;
- response_body — JSONB, сохраненное тело исходного успешного ответа;
- resource_id — UUID, идентификатор созданного ресурса, допускается NULL;
- created_at — дата и время создания;
- expires_at — дата и время окончания хранения ключа.

Связи:
- каждая IdempotencyKey принадлежит ровно одному User;
- один User может иметь несколько IdempotencyKey;
- IdempotencyKey может ссылаться на созданную Subscription или Payment через resource_id и operation.

Ограничения:
- комбинация user_id, key и operation должна быть уникальной;
- повторный запрос с теми же user_id, key, operation и request_hash должен возвращать сохраненный результат без повторного выполнения операции;
- повторное использование ключа с другим request_hash должно возвращать HTTP 409 Conflict;
- создание IdempotencyKey и соответствующего финансового ресурса должно выполняться атомарно;
- response_status и response_body заполняются только для успешных ответов 2xx и хранятся 24 часа; ошибки валидации и 5xx не сохраняются как результат операции.

6.7. AuditLog — журнал аудита

Сущность AuditLog должна хранить историю значимых действий пользователей и системных операций, влияющих на учетные записи и финансовые данные.

Обязательные поля:
- id — UUID, первичный ключ;
- user_id — UUID, внешний ключ на User.id; допускается NULL для системного события после удаления пользователя;
- entity_type — строка, тип затронутой сущности;
- entity_id — UUID, идентификатор затронутой записи;
- action — строка или перечисление, выполненное действие;
- old_values — JSONB, прежние значения измененных полей, если применимо;
- new_values — JSONB, новые значения измененных полей, если применимо;
- created_at — дата и время события;
- request_id — идентификатор запроса, если событие вызвано API-запросом.

Связи:
- AuditLog может быть связан с одним User;
- AuditLog не должен иметь жесткой внешней связи с конкретной бизнес-сущностью, поскольку журнал должен сохраняться даже после архивирования или удаления соответствующей записи.

В AuditLog должны регистрироваться как минимум:
- создание, изменение, архивирование подписки;
- создание платежа;
- регистрация возврата;
- корректировка или отмена финансовой операции;
- изменение категории;
- смена email и пароля;
- отзыв сессий;
- удаление учетной записи.

В журнал запрещено записывать пароли, access token, refresh token и другие секреты.

6.8. Итоговые связи между сущностями

В базе данных должны быть реализованы следующие связи:

1. User 1:N Subscription — один пользователь может иметь несколько подписок. Каждая подписка принадлежит только одному пользователю.
2. User 1:N Payment — один пользователь может иметь несколько платежей. Каждый платеж принадлежит только одному пользователю.
3. User 1:N Category — один пользователь может создавать несколько собственных категорий. Системные категории могут иметь user_id=NULL.
4. User 1:N AuthSession — один пользователь может иметь несколько сессий аутентификации.
5. User 1:N IdempotencyKey — один пользователь может иметь несколько ключей идемпотентности.
6. User 1:N AuditLog — действия пользователя могут создавать несколько записей аудита.
7. Category 1:N Subscription — одна категория может быть назначена нескольким подпискам.
8. Category 1:N Payment — одна категория может быть указана у нескольких платежей.
9. Subscription 1:N Payment — одна подписка может иметь несколько фактических платежей. Платеж может не иметь subscription_id, если он является разовым расходом.
10. Payment 1:N Payment — одна исходная операция списания может иметь несколько связанных операций возврата. Для возврата original_payment_id указывает на исходную операцию.
11. AuthSession 1:1 или 1:N self-reference через replaced_by_session_id — сессия может ссылаться на сессию, созданную при ротации refresh token; все сессии одного семейства объединяются через token_family_id.

6.9. Правила удаления и ссылочной целостности

- При удалении пользователя все его AuthSession должны быть отозваны.
- При удалении пользователя его подписки, платежи и пользовательские категории должны обрабатываться согласованно в рамках одной транзакции либо процедуры удаления учетной записи.
- Физическое удаление платежей и возвратов запрещено обычными пользовательскими операциями.
- Удаление или архивирование подписки не должно удалять связанные платежи.
- Удаление категории не должно приводить к потере исторической информации о категории в платежах.
- Внешние ключи и уникальные ограничения должны обеспечиваться PostgreSQL, а не только проверками приложения.
- Все операции, затрагивающие несколько связанных сущностей, должны выполняться в транзакции базы данных.

7.1. Общие правила обработки данных

7.1.1. Идентификация пользователя и владение данными

1. Все операции с пользовательскими данными выполняются в контексте аутентифицированного user_id, полученного из access token. Переданный клиентом user_id не является доверенным источником и не используется для определения владельца создаваемой записи.
2. Для Subscription, Payment, Category, AuthSession и IdempotencyKey принадлежность текущему пользователю проверяется на backend-уровне. Проверка должна выполняться в рамках того же запроса и транзакции, в которых изменяется запись.
3. Для связей Payment → Subscription, Payment → Category и Subscription → Category должны проверяться одновременно существование записи и ее доступность текущему пользователю либо системный статус Category.
4. При обращении к ресурсу другого пользователя API возвращает 404 Not Found, а не 403 Forbidden. Это правило применяется к получению, изменению, архивированию и операциям над платежами.
5. Системные категории доступны для чтения всем пользователям, но не могут изменяться, удаляться или деактивироваться через пользовательский API.

7.1.2. Форматы дат и времени

1. Все timestamp-поля в БД хранятся как TIMESTAMPTZ в UTC. Даты подписок и даты начала платежного периода хранятся как DATE.
2. Входящий datetime должен содержать часовой пояс или UTC offset. Значение без часового пояса для datetime-поля отклоняется с 422 VALIDATION_ERROR.
3. В ответах API timestamp возвращается в UTC в ISO 8601, например 2026-11-15T07:30:00Z. Поля типа date возвращаются в формате YYYY-MM-DD.
4. Часовой пояс пользователя задается IANA-идентификатором, например Europe/Vilnius. Некорректный или неизвестный идентификатор часового пояса отклоняется.
5. Параметры date_from и date_to в истории и аналитике трактуются как локальные календарные даты часового пояса пользователя. Интервал всегда полуоткрытый: date_from включается, date_to не включается. Локальные границы преобразуются в UTC до выполнения запроса. Для due_from и due_to в списке подписок действует такое же правило включения левой и исключения правой границы по календарной дате next_payment_date.
6. Если date_to не передан, верхняя граница не применяется. Это правило относится к GET /payments и другим списковым фильтрам, для которых контракт явно объявляет date_to необязательным. Для GET /analytics/summary, GET /analytics/monthly и GET /analytics/categories обе границы date_from и date_to обязательны. Если переданы обе границы, date_from должен быть меньше date_to.
7. Месяц аналитики определяется по локальному времени пользователя, а не по UTC-дате occurred_at.
8. Если timezone не задан при регистрации, используется UTC. Если preferred_currency не задан, используется валидная валюта из настройки приложения DEFAULT_CURRENCY; приложение не должно запускаться с некорректным значением этой настройки.

7.1.3. Денежные значения и валюты

1. Денежные значения передаются в JSON строками, например "15.99". Числовые JSON-литералы для amount и итоговых денежных значений не используются.
2. В Python денежные значения обрабатываются через Decimal. Использование float запрещено на всех этапах вычислений.
3. В PostgreSQL денежные поля хранятся в NUMERIC(20, 8). На уровне API сумма должна быть положительной и иметь не больше знаков после запятой, чем допускает minor unit соответствующей валюты по актуальному справочнику ISO 4217. Избыточная точность отклоняется, автоматическое округление входящего значения не выполняется.
4. Валюта передается трехбуквенным кодом ISO 4217 в верхнем регистре. Одной проверки регулярного выражения недостаточно. Приложение использует единый справочник SUPPORTED_CURRENCIES, содержащий код валюты и ее minor unit. Наличие кода проверяется по данным pycountry, допустимое число дробных знаков — по данным Babel/CLDR; версии библиотек фиксируются в зависимостях проекта. Справочник обновляется только вместе с релизом приложения. Код, отсутствующий в справочнике, отклоняется с 422 VALIDATION_ERROR.
5. Суммы в разных валютах не складываются. Фильтр currency применяется до группировки, а ответ без такого фильтра содержит отдельную группу для каждой валюты.
6. preferred_currency является валютой отображения и не вызывает автоматическую конвертацию аналитики. Конвертация не выполняется в версии 1.
7. Для суммы, не соответствующей допустимой точности валюты, возвращается 422 VALIDATION_ERROR с указанием поля amount и допустимого количества десятичных знаков.

7.1.4. Общая валидация

1. UUID принимаются в стандартном формате UUID. Некорректный формат отклоняется с 422.
2. Строковые значения очищаются от пробелов по краям. Пустая после очистки обязательная строка отклоняется.
3. service_name: от 1 до 200 символов. name категории: от 1 до 100 символов. description: не более 2000 символов. Цвет категории: HEX-формат #RRGGBB.
4. interval_count — целое число от 1 до 1200 включительно. Поддерживаются только day, week, month, year.
5. Для списковых endpoint-ов limit по умолчанию равен 20, минимальное значение — 1, максимальное — 100; offset по умолчанию равен 0 и не может быть отрицательным.
6. Поля, отсутствующие в PATCH-запросе, не изменяются. Явное null разрешается только для nullable-полей и означает очистку значения. Для обязательных полей null отклоняется.
7. Неизвестные поля входных JSON-схем отклоняются с 422, если иное явно не предусмотрено контрактом endpoint-а.

7.2. Правила жизненного цикла учетной записи и аутентификации

7.2.1. Регистрация и подтверждение email

1. Email нормализуется: удаляются пробелы по краям, адрес приводится к принятому для приложения регистронезависимому представлению. Уникальность обеспечивается для нормализованного адреса на уровне PostgreSQL.
2. После регистрации is_active=true, is_verified=false. Доступ к защищенным endpoint-ам разрешается только после подтверждения email, если обязательная проверка включена в конфигурации приложения.
3. Токен подтверждения email является одноразовым, криптографически случайным, хранится на сервере только в виде хеша и действует 24 часа.
4. Повторное использование, истечение срока или отзыв токена приводит к 400 INVALID_OR_EXPIRED_TOKEN. Успешное подтверждение помечает токен использованным в той же транзакции, в которой обновляется is_verified.
5. Повторный запрос письма подтверждения для уже подтвержденного адреса не создает новую активную цепочку токенов; API возвращает 202 Accepted без раскрытия лишних сведений.

7.2.2. Пароли и восстановление

1. Минимальная длина нового пароля — 12 символов, максимальная — 128 символов. Пароль не должен совпадать с email. Сложность и проверка распространенных паролей дополнительно задаются политикой безопасности приложения.
2. Пароль хешируется Argon2id либо другим согласованным специализированным алгоритмом. Открытый пароль не сохраняется и не логируется.
3. Токен восстановления пароля одноразовый, хранится в виде хеша и действует 30 минут.
4. Ответ POST /auth/forgot-password всегда имеет одинаковый код и структуру независимо от существования email.
5. При успешном сбросе пароля старый токен помечается использованным, а все AuthSession пользователя отзываются. Ранее выданные refresh token после этого не могут быть использованы.
6. При авторизованной смене пароля пользователь должен передать текущий пароль. После успешной смены пароля все refresh-сессии пользователя отзываются; клиент выполняет повторную авторизацию.

7.2.3. Access и refresh token

1. Access token — JWT со сроком жизни 15 минут. Он передается в Authorization: Bearer и не хранится в БД.
2. Refresh token — непрозрачное случайное значение достаточной криптографической стойкости, срок жизни 30 дней. В AuthSession хранится только его хеш.
3. При каждом успешном refresh старый refresh token атомарно отзывается, создается новая AuthSession с тем же token_family_id и устанавливается связь replaced_by_session_id.
4. Повторное использование отозванного refresh token является признаком компрометации: все сессии с соответствующим token_family_id отзываются в одной транзакции.
5. Для браузерного клиента refresh token передается только в cookie с HttpOnly, Secure и SameSite=Lax либо более строгим значением, совместимым с клиентом. Cookie имеет Path=/api/v1/auth и Max-Age, соответствующий сроку жизни токена. Refresh token не включается в JSON-ответ.
6. Запросы, использующие refresh cookie, требуют CSRF-защиты по схеме double-submit cookie. При login и refresh сервер устанавливает отдельную cookie csrf_token с криптографически случайным значением, атрибутами Secure, Path=/api/v1/auth и тем же SameSite, что у refresh cookie; HttpOnly для этой cookie не устанавливается, чтобы клиент мог прочитать значение. Клиент передает его в X-CSRF-Token. Сервер сравнивает заголовок и cookie алгоритмом сравнения за постоянное время и ротирует CSRF-значение вместе с refresh token. Access token продолжает передаваться через Bearer. CSRF token не является access token и не дает права доступа сам по себе.
7. Выход отзывает refresh-сессию текущего клиента и очищает cookie. Выданный access token может оставаться действительным до истечения его 15-минутного срока.
8. Удаление учетной записи, сброс и смена пароля отзывают все refresh-сессии пользователя.

7.2.4. Изменение email

1. Запрос смены email требует действующий access token и подтверждение текущего пароля.
2. До подтверждения нового адреса email пользователя не меняется. Нормализованный новый адрес сохраняется в User.pending_email, а срок резервации — в User.pending_email_reserved_until. Резервация действует до истечения токена. В транзакции инициации и подтверждения проверяется отсутствие адреса как в User.email, так и в активных User.pending_email других учетных записей; уникальность активных резерваций дополнительно обеспечивается частичным уникальным индексом PostgreSQL по lower(pending_email).
3. Токен подтверждения нового email отправляется на новый адрес, одноразовый и действует 24 часа.
4. После подтверждения выполняется атомарная смена email. Все refresh-сессии пользователя отзываются, пользователь должен войти повторно.
5. Если новый адрес уже принадлежит другому пользователю, возвращается 409 EMAIL_ALREADY_EXISTS.

7.2.5. Удаление учетной записи

1. Удаление требует аутентификации, повторного ввода пароля и явного подтверждения операции строкой DELETE.
2. В одной транзакции отзываются сессии, удаляются пользовательские IdempotencyKey и OneTimeToken, подписки, платежи и пользовательские категории, а учетная запись удаляется. Это единственный пользовательский сценарий, в котором физическое удаление платежей допускается как часть полного удаления учетной записи; обычные API платежей не предоставляют физическое удаление.
3. Системные категории не удаляются.
4. Для сохранения факта выполнения операции в AuditLog создается обезличенное системное событие с user_id=NULL. В old_values и new_values запрещено сохранять email, пароль, токены и иные прямые персональные данные удаленного пользователя.
5. Если транзакция удаления не завершилась полностью, изменения откатываются и учетная запись остается доступной.

7.3. Правила периодичности и жизненного цикла подписки

7.3.1. Точка отсчета расписания

1. start_date — неизменяемая дата первого платежа, заданная при создании подписки.
2. Для однозначного сохранения исходного дня месяца и пересчета расписания вводится дополнительное поле Subscription.schedule_anchor_date типа DATE. При создании оно равно start_date. Это техническое поле необходимо добавить к описанию модели Subscription; оно не заменяет start_date.
3. Для day и week очередная дата вычисляется как schedule_anchor_date + N дней/недель. Для month и year вычисление выполняется календарной арифметикой непосредственно от schedule_anchor_date, а не последовательным прибавлением периода к предыдущей ограниченной дате.
4. Для month сохраняется номер дня schedule_anchor_date. Если в целевом месяце такого дня нет, используется последний календарный день месяца. Например, якорь 31 января дает 28/29 февраля, затем 31 марта.
5. Для year сохраняются месяц и день якоря. Если якорь — 29 февраля, в невисокосный год дата платежа приходится на 28 февраля, а в следующий високосный год снова на 29 февраля.
6. При создании подписки next_payment_date равен первой дате расписания, которая не раньше текущей локальной даты пользователя. Пропущенные до создания подписки периоды автоматически не превращаются в платежи.
7. При изменении next_payment_date вручную новое значение становится schedule_anchor_date для дальнейших платежей. start_date при этом не меняется.
8. При изменении billing_interval_unit или interval_count текущий next_payment_date сохраняется и становится новой schedule_anchor_date; будущие даты строятся с новым интервалом. Изменение одного параметра не должно менять уже зарегистрированные платежи.
9. amount, currency, service_name и category_id не меняют даты расписания.

7.3.2. Оплата периода и сдвиг next_payment_date

1. Для платежа, связанного с подпиской, billing_period_start обязателен и обозначает дату конкретного планового платежа, за который внесена оплата.
2. billing_period_start не может быть раньше start_date. Для периода, начиная с schedule_anchor_date, дата должна соответствовать одной из дат текущего расписания. Для периодов до текущего schedule_anchor_date допускается историческая ручная регистрация, поскольку расписание могло быть изменено после таких периодов.
3. Если billing_period_start равен текущему next_payment_date, после успешного создания платежа next_payment_date атомарно сдвигается на первую дату расписания строго позже оплаченного периода.
4. Если billing_period_start меньше next_payment_date, платеж считается историческим; next_payment_date не меняется.
5. Если billing_period_start больше next_payment_date, запрос отклоняется с 409 FUTURE_BILLING_PERIOD_NOT_ALLOWED. Для оплаты следующего периода пользователь сначала должен зарегистрировать текущий период либо изменить дату следующего платежа отдельным PATCH.
6. Для одной подписки допускается не более одного платежа charge со статусом pending или succeeded на один billing_period_start. Неуспешный платеж со статусом failed не блокирует повторную регистрацию.
7. При регистрации платежа строка Subscription блокируется на время транзакции. Проверка периода, создание Payment и сдвиг next_payment_date выполняются атомарно.
8. Фактическая сумма платежа не обязана совпадать с текущей стоимостью подписки: в Payment фиксируется фактически уплаченная сумма. Валюта для нового платежа, связанного с подпиской, должна совпадать с текущей валютой подписки.
9. Если валюта подписки была изменена, исторический платеж в прежней валюте можно внести как разовый Payment без subscription_id. Для привязки нового платежа к подписке используется только текущая валюта подписки.
10. Регистрация платежа разрешена также для подписки со статусом paused, если выполнены правила billing_period_start. Такой платеж фиксирует фактический расход, но не снимает паузу. Сдвиг next_payment_date выполняется по общим правилам; подписка остается paused и не включается в прогноз до явного возобновления.

7.3.3. Статусы подписки

1. Допустимые переходы: active → paused; active → cancelled; paused → active; paused → cancelled. cancelled является терминальным статусом и повторная активация отмененной подписки не поддерживается; для продолжения создается новая подписка.
2. При paused расписание сохраняется, но подписка не включается в прогноз. При возобновлении система выбирает первую дату расписания, которая не раньше текущей локальной даты пользователя. Пропущенные во время паузы даты не генерируют задолженность и не включаются в прогноз.
3. При cancelled подписка не включается в прогноз и не генерирует будущие платежи. История платежей сохраняется.
4. is_archived — отдельный признак скрытия записи, а не финансовый статус. Архивная подписка не включается в обычный список и прогноз. Она доступна владельцу через GET по идентификатору и через список с include_archived=true, но PATCH для нее запрещен с 409 SUBSCRIPTION_ARCHIVED. Создание новых платежей с subscription_id архивной подписки запрещено. Для изменения или внесения исторической записи такую подписку предварительно необходимо восстановить.
5. Архивирование не меняет status и не удаляет платежи. Повторный DELETE для уже архивной подписки возвращает 204.
6. Если требуется восстановление, используется POST /subscriptions/{subscription_id}/restore. Восстановление не переводит cancelled в active; статус cancelled остается терминальным. Архивная paused-подписка после восстановления остается paused.

7.4. Правила платежей

7.4.1. Создание платежа

1. Пользовательский POST /payments создает только списание: payment_type=charge, status=succeeded, source=manual. Эти поля устанавливаются сервером и не принимаются от клиента.
2. Для платежа, связанного с подпиской, subscription_id должен принадлежать текущему пользователю. Для архивной подписки возвращается 409 SUBSCRIPTION_ARCHIVED, для cancelled — 409 SUBSCRIPTION_NOT_ACTIVE. Подписка paused допускает регистрацию фактического платежа без снятия паузы. Валюта должна совпадать с текущей валютой подписки, billing_period_start обязателен.
3. Если category_id не передан для платежа по подписке, используется категория подписки. Если category_id передан явно, он должен быть системным либо принадлежать текущему пользователю; это позволяет отнести конкретную оплату к другой категории.
4. Если subscription_id не передан, service_name обязателен и становится service_name_snapshot. Такой платеж считается разовым расходом.
5. Для связанного платежа service_name_snapshot копируется из Subscription.service_name. category_snapshot копируется из фактически выбранной категории. Изменения исходных сущностей в дальнейшем не меняют снимки.
6. Платежи не имеют пользовательских PATCH и DELETE. Исправление выполняется отдельной операцией reverse с записью причины и AuditLog.
7. В первой версии источник manual устанавливается сервером. Источники import и provider зарезервированы для будущих доверенных интеграций и не могут задаваться обычным пользователем.
8. occurred_at платежа не может быть позже текущего момента UTC более чем на 5 минут допустимого расхождения часов. Нарушение отклоняется с 422 VALIDATION_ERROR.

7.4.2. Статусы платежей

1. pending — операция ожидает завершения; не включается в фактические расходы, но резервирует платежный период и сумму возможного возврата, если это возврат.
2. succeeded — успешно завершенная операция; включается в аналитику.
3. failed — неуспешная операция; не включается в аналитику и не резервирует платежный период после фиксации этого статуса.
4. reversed — полностью отмененная операция; не включается в аналитику. Для ручных платежей версии 1 статус succeeded может быть переведен в reversed только через специальный endpoint reverse, если по нему еще нет возвратов.
5. Допустимые переходы: pending → succeeded; pending → failed; pending → reversed; succeeded → reversed только по правилам полного сторнирования; failed и reversed являются терминальными статусами.
6. Обычный пользовательский POST /payments сразу создает succeeded. Переходы pending и failed предназначены для будущих интеграций и внутренних системных процессов.

7.5. Правила возвратов и сторнирования

1. Возврат создается только для исходного Payment с payment_type=charge и status=succeeded. Возврат на возврат запрещен.
2. Сумма возврата строго положительная, валюта наследуется от исходного платежа и не может быть изменена клиентом. occurred_at возврата не может быть раньше occurred_at исходного платежа и не может быть позже текущего момента UTC более чем на 5 минут допустимого расхождения часов.
3. Возврат копирует user_id, subscription_id, billing_period_start, category_id, service_name_snapshot и category_snapshot исходного платежа. В аналитике возврат учитывается в периоде собственного occurred_at.
4. Сумма успешных и ожидающих возвратов по исходному платежу не может превышать сумму исходного успешного списания. В проверку лимита включаются succeeded и pending; failed и reversed не учитываются.
5. Конкурирующие запросы возврата сериализуются блокировкой исходной строки Payment через SELECT FOR UPDATE. Проверка остатка и создание возврата выполняются в одной транзакции.
6. Возврат в версии 1, создаваемый пользователем вручную, имеет status=succeeded и source=manual.
7. Полное сторнирование ошибочного списания выполняется через POST /payments/{payment_id}/reverse. Сторнирование разрешено только для succeeded charge без связанных возвратов. В результате исходная запись получает status=reversed, а причина фиксируется в AuditLog. Отдельная запись refund при таком исправлении не создается.
8. Если по исходному списанию уже зарегистрирован хотя бы один успешный или ожидающий возврат, полное сторнирование запрещено. Для реального возврата средств используется операция refund.
9. Финансовые записи и возвраты не удаляются физически обычными API-операциями. Исправление не должно скрывать исходную запись из аудита.

7.6. Идемпотентность и защита от дублей

1. Idempotency-Key обязателен для POST /subscriptions, POST /payments и POST /payments/{payment_id}/refunds. Значение ключа — строка длиной от 16 до 128 символов.
2. Область уникальности: user_id + operation + key. operation включает HTTP-метод и нормализованный путь endpoint-а.
3. request_hash рассчитывается сервером от нормализованного тела запроса и существенных параметров операции. Токены и секреты в hash не включаются.
4. При повторном запросе с тем же ключом и тем же request_hash возвращаются сохраненные HTTP-статус и тело первоначального успешного ответа; бизнес-операция повторно не выполняется.
5. При повторном использовании того же ключа для другой операции или с другим request_hash возвращается 409 IDEMPOTENCY_KEY_REUSED.
6. Сохранение IdempotencyKey и бизнес-ресурса выполняется в одной транзакции. Если транзакция откатывается, ключ и ресурс не сохраняются.
7. Для параллельных запросов с одним ключом используется уникальное ограничение БД. Если первая транзакция еще выполняется, второй запрос ожидает завершения конкурирующей вставки на уровне PostgreSQL. После фиксации первой транзакции второй запрос возвращает сохраненный результат без повторного выполнения операции; после ее отката второй запрос выполняет операцию самостоятельно. Одно только совпадение по времени не является основанием для 409.
8. Успешные ответы 2xx сохраняются на 24 часа. После истечения срока запись может быть удалена фоновым процессом. Ошибки валидации и 5xx не кэшируются как результат операции.
9. Идемпотентность не заменяет ограничение уникальности платежа за billing_period_start: для подписки также действует уникальный частичный индекс по subscription_id и billing_period_start для charge со статусом pending или succeeded.

7.7. Правила категорий

1. Пользовательская категория имеет user_id текущего пользователя и is_system=false. Системная категория имеет user_id=NULL и is_system=true.
2. Название пользовательской категории уникально без учета регистра в пределах одного пользователя. Одинаковые названия у разных пользователей допустимы.
3. При DELETE категория деактивируется (is_active=false), физически не удаляется. Системная категория через этот endpoint не деактивируется.
4. При деактивации категории ее назначение у подписок текущего пользователя очищается (Subscription.category_id=NULL). Исторические Payment.category_id и category_snapshot сохраняются.
5. Неактивная категория не может назначаться новым подпискам и платежам. Уже существующие платежи продолжают отображаться и участвовать в аналитике.
6. Категорию можно повторно активировать через PATCH is_active=true, если она принадлежит текущему пользователю.
7. При отсутствии категории аналитика группирует операцию в отдельную группу без категории; category_id и category_name в ответе равны null, display_name может быть "Без категории".
8. Для исторической аналитики используется category_snapshot, сохраненный в Payment на момент операции. При группировке учитывается пара category_id + category_snapshot; это позволяет не переименовывать прошлые операции при изменении названия категории.

7.8. Правила фактической аналитики

1. В фактические расходы включаются только записи Payment со status=succeeded. pending, failed и reversed исключаются.
2. gross_charges — сумма succeeded charge; refunds — сумма succeeded refund; net_expenses = gross_charges - refunds.
3. Возврат учитывается в периоде его собственного occurred_at. Исходное списание остается в периоде исходного occurred_at.
4. payments_count в summary и categories означает число всех учитываемых успешных операций (charge и refund). При необходимости отдельные количества возвращаются как charges_count и refunds_count.
5. Все суммы группируются по currency. Ни один endpoint не возвращает общий итог, полученный сложением разных валют.
6. Интервал аналитики полуоткрытый [date_from, date_to), в локальном времени пользователя. Если фильтр currency отсутствует, ответ содержит все валюты раздельно.
7. В monthly возвращаются все календарные месяцы, пересекающие заданный период, включая месяцы без операций; суммы отсутствующих операций равны "0.00". В каждый месяц включаются только операции внутри исходного полуоткрытого периода [date_from, date_to). Поэтому первый и последний месяцы ответа могут содержать частичные календарные месяцы, а не суммы за весь месяц.
8. В categories группировка производится по фактическому снимку категории из Payment, а не по текущей категории Subscription или текущему названию Category.
9. Аналитика не включает ожидаемые платежи из Subscription. Прогноз возвращается только через /analytics/upcoming.

7.9. Правила прогноза

1. По умолчанию прогноз строится на следующий календарный месяц относительно текущей локальной даты пользователя.
2. Параметр month позволяет выбрать текущий или будущий календарный месяц в формате YYYY-MM. Месяц, полностью находящийся в прошлом, отклоняется с 422.
3. В прогноз включаются только Subscription со status=active и is_archived=false.
4. Для каждой подписки перечисляются все даты расписания внутри выбранного календарного месяца, начиная с next_payment_date. Для частых интервалов учитывается каждая дата. Если выбран текущий месяц, даты раньше текущей локальной даты исключаются из прогноза; вычисление прогноза не изменяет next_payment_date.
5. Прогнозируемая сумма равна текущему amount подписки для каждой ожидаемой даты. Пропорциональный расчет, налоги, комиссии, скидки и конвертация валют не выполняются.
6. Платеж за период, уже зарегистрированный как succeeded или pending, не должен повторно включаться в прогноз. При успешной регистрации платежа за текущий период next_payment_date сдвигается, что исключает повторное включение.
7. Прогноз группируется отдельно по валюте и категории. Подписка без категории попадает в группу null/"Без категории".
8. Прогноз не создает Payment и не изменяет Subscription. Он вычисляется по текущим параметрам подписок на момент запроса.

7.10. Дополнительные технические ограничения целостности

1. Для Subscription рекомендуется добавить schedule_anchor_date DATE NOT NULL с начальным значением start_date.
2. Для OneTimeToken рекомендуется добавить отдельную таблицу одноразовых токенов: id UUID, user_id UUID, token_hash, token_type (verify_email, reset_password, change_email), expires_at TIMESTAMPTZ, used_at TIMESTAMPTZ NULL, created_at TIMESTAMPTZ. Уникальность token_hash обязательна. Это обеспечивает одноразовость токенов подтверждения и восстановления.
3. Для Subscription обеспечить UNIQUE(id, user_id) и составной внешний ключ Payment(user_id, subscription_id) → Subscription(user_id, id). Для Category обеспечить UNIQUE(id, user_id) для пользовательских категорий; правило, что category.user_id IS NULL либо category.user_id совпадает с владельцем Subscription/Payment, должно дополнительно проверяться триггером PostgreSQL или эквивалентным ограничением БД. Одной проверки приложения недостаточно.
4. Для Payment создать частичный уникальный индекс по (subscription_id, billing_period_start) для payment_type='charge' и status IN ('pending','succeeded'), когда subscription_id и billing_period_start не NULL.
5. Для пользовательских Category создать уникальный индекс по (user_id, lower(name)) для is_system=false и активных/неактивных категорий, чтобы повторное создание одинакового названия после деактивации не обходило уникальность.
6. Для IdempotencyKey создать UNIQUE(user_id, operation, key). Для AuthSession — UNIQUE(refresh_token_hash).
7. Все изменения Subscription и Payment, которые затрагивают несколько сущностей, выполняются в транзакциях. Возвраты и изменение next_payment_date обязательно используют блокировки строк соответствующих исходных записей.
8. AuditLog является append-only: обычный API не изменяет и не удаляет записи. Пароли, токены, cookie, секреты, полный номер платежного инструмента и иные секреты в AuditLog не записываются.

8. ПОЛНЫЕ API-КОНТРАКТЫ
======================================================================

8.1. Общие правила API

8.1.1. Базовый адрес и формат

1. Базовый URL: /api/v1.
2. Все JSON endpoint-ы принимают Content-Type: application/json и возвращают application/json, кроме POST /auth/jwt/login, который принимает application/x-www-form-urlencoded, и endpoint-ов с ответом 204 No Content.
3. Все защищенные endpoint-ы требуют Authorization: Bearer <access_token>.
4. Для POST /subscriptions, POST /payments и POST /payments/{payment_id}/refunds обязателен заголовок Idempotency-Key. При его отсутствии возвращается 422 IDEMPOTENCY_KEY_REQUIRED; при значении вне диапазона 16–128 символов — 422 VALIDATION_ERROR с указанием поля Idempotency-Key.
5. Все timestamp-поля передаются в ISO 8601 с offset и возвращаются в UTC с суффиксом Z.
6. Денежные поля в запросах и ответах — JSON-строки.
7. Параметры date_from и date_to являются локальными датами пользователя. date_from включается, date_to исключается.

8.1.2. Общий формат ошибки

Любая ошибка, кроме ответа 204, возвращается в следующем формате:

{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid request data",
    "details": {
      "field": "amount",
      "reason": "Amount has too many decimal places"
    },
    "request_id": "uuid"
  }
}

Основные коды:
- VALIDATION_ERROR — 422, ошибка формата или проверки полей;
- IDEMPOTENCY_KEY_REQUIRED — 422, обязательный заголовок Idempotency-Key отсутствует;
- UNAUTHENTICATED — 401, отсутствует или недействителен access token;
- INVALID_CREDENTIALS — 400, неверные учетные данные или текущий пароль;
- INVALID_REFRESH_TOKEN — 401, refresh token отсутствует, истек, отозван или использован повторно;
- EMAIL_NOT_VERIFIED — 403, обязательное подтверждение email не выполнено;
- EMAIL_ALREADY_EXISTS — 409, email уже используется;
- RESOURCE_NOT_FOUND — 404, запись не найдена или принадлежит другому пользователю;
- CATEGORY_NOT_AVAILABLE — 409, категория недоступна для назначения;
- SUBSCRIPTION_NOT_ACTIVE — 409, отмененная подписка не допускает новую регистрацию платежа;
- SUBSCRIPTION_ARCHIVED — 409, операция недопустима до восстановления архивной подписки;
- CATEGORY_ALREADY_EXISTS — 409, название пользовательской категории уже занято;
- SYSTEM_CATEGORY_READ_ONLY — 403, системная категория доступна только для чтения;
- DUPLICATE_BILLING_PERIOD — 409, для периода уже есть pending/succeeded списание;
- FUTURE_BILLING_PERIOD_NOT_ALLOWED — 409, billing_period_start позже next_payment_date;
- CURRENCY_MISMATCH — 422, валюта платежа не совпадает с валютой подписки или исходного платежа;
- REFUND_LIMIT_EXCEEDED — 409, сумма возвратов превысит исходный платеж;
- REFUND_NOT_ALLOWED — 409, возврат для исходной операции недопустим;
- PAYMENT_ALREADY_REVERSED — 409, операция уже сторнирована;
- REVERSAL_NOT_ALLOWED — 409, операция не может быть сторнирована;
- IDEMPOTENCY_KEY_REUSED — 409, ключ использован с другим телом или endpoint-ом;
- INVALID_OR_EXPIRED_TOKEN — 400, одноразовый токен недействителен, истек или уже использован;
- RATE_LIMIT_EXCEEDED — 429, превышен лимит запросов;
- INTERNAL_ERROR — 500, непредвиденная ошибка сервера.

В details допускаются имя поля, причина, допустимые значения и идентификатор конфликтующей операции, если его раскрытие безопасно. Стек вызовов и внутренние секреты клиенту не возвращаются.

8.1.3. Общий контракт списков

Все списковые endpoint-ы, кроме аналитических ответов, используют структуру:

{
  "items": [],
  "pagination": {
    "total": 0,
    "limit": 20,
    "offset": 0
  }
}

limit по умолчанию 20, диапазон 1–100; offset по умолчанию 0. total — общее число записей после применения фильтров, но до пагинации. Сортировка принимается только по полям, перечисленным в контракте соответствующего endpoint-а. Неизвестное поле сортировки возвращает 422.

8.2. API регистрации и авторизации

8.2.1. POST /auth/register

Назначение: создание учетной записи.
Доступ: публичный.
Заголовки: Content-Type: application/json.

Запрос:
{
  "email": "user@example.com",
  "password": "StrongPassword123!"
}

Проверки: email корректен и уникален после нормализации; пароль соответствует правилам 7.2.2. Поля is_active, is_verified, is_superuser и user_id клиентом не задаются.

Успешный ответ: 201 Created.
{
  "id": "uuid",
  "email": "user@example.com",
  "is_active": true,
  "is_verified": false,
  "created_at": "2026-11-01T10:00:00Z"
}

После создания инициируется письмо подтверждения email. При занятом адресе — 409 EMAIL_ALREADY_EXISTS. При ошибке валидации — 422.

8.2.2. POST /auth/jwt/login

Назначение: вход пользователя.
Доступ: публичный.
Формат запроса: application/x-www-form-urlencoded.

Поля формы:
- username — email пользователя;
- password — пароль.

Успешный ответ: 200 OK.
{
  "access_token": "access.jwt.token",
  "token_type": "bearer",
  "expires_in": 900
}

Refresh token возвращается исключительно в Set-Cookie согласно правилу 7.2.3 и в JSON не включается. Для неподтвержденного email, если подтверждение обязательно, возвращается 403 EMAIL_NOT_VERIFIED. Для неверных учетных данных возвращается 400 INVALID_CREDENTIALS без уточнения, какое поле неверно.

8.2.3. POST /auth/refresh

Назначение: ротация refresh token и получение новой пары токенов.
Доступ: без Bearer access token; необходима действительная refresh cookie и CSRF-защита.
Заголовки: X-CSRF-Token.
Тело: отсутствует.

Успешный ответ: 200 OK.
{
  "access_token": "new_access.jwt.token",
  "token_type": "bearer",
  "expires_in": 900
}

Новый refresh token устанавливается в Set-Cookie. Старый токен атомарно отзывается. Повторное использование старого токена отзывает все сессии его token_family_id и возвращает 401 INVALID_REFRESH_TOKEN. Отсутствующий, истекший или отозванный токен также дает 401.

8.2.4. POST /auth/jwt/logout

Назначение: выход из текущей refresh-сессии.
Доступ: Bearer access token и действующая refresh cookie; для cookie требуется CSRF-защита.
Тело: отсутствует.

Успешный ответ: 204 No Content. Refresh-сессия отзывается, cookie очищается через Set-Cookie с истекшим сроком. Access token действует до истечения собственного срока жизни.

8.2.5. POST /auth/forgot-password

Назначение: запрос письма для восстановления пароля.
Доступ: публичный.
Запрос:
{
  "email": "user@example.com"
}

Успешный ответ всегда: 202 Accepted.
{
  "message": "If the account exists, instructions have been sent."
}

Ответ одинаков для существующего и несуществующего email. Для существующего пользователя отправляется одноразовый токен сроком 30 минут. Применяются rate limits.

8.2.6. POST /auth/reset-password

Назначение: установка нового пароля по токену восстановления.
Доступ: публичный.
Запрос:
{
  "token": "one_time_reset_token",
  "password": "NewStrongPassword123!"
}

8.4.4. PATCH /subscriptions/{subscription_id}

Назначение: частичное изменение подписки.
Доступ: защищенный.
Запрос — любое непустое сочетание:
{
  "service_name": "Netflix Premium",
  "description": "Updated plan",
  "amount": "19.99",
  "currency": "EUR",
  "billing_interval_unit": "month",
  "interval_count": 1,
  "next_payment_date": "2026-12-15",
  "category_id": "another-uuid",
  "status": "paused"
}

Разрешены только service_name, description, amount, currency, billing_interval_unit, interval_count, next_payment_date, category_id и status. is_archived, user_id, start_date и schedule_anchor_date напрямую клиентом не задаются.

Правила:
- если передан next_payment_date, он становится новым schedule_anchor_date;
- если меняется billing_interval_unit или interval_count, текущий next_payment_date становится новым schedule_anchor_date;
- если изменяются одновременно периодичность и next_payment_date, anchor равен явно переданному next_payment_date;
- изменение суммы, валюты, названия или категории не изменяет ранее созданные Payment;
- для смены currency с существующей историей новые платежи должны соответствовать новой валюте, прежняя история сохраняет собственную currency;
- переходы status выполняются только по правилам 7.3.3;
- для архивной подписки PATCH запрещен и возвращает 409 SUBSCRIPTION_ARCHIVED; сначала необходимо выполнить restore.

Успешный ответ: 200 OK — полный объект подписки. Чужая запись — 404; недопустимый переход — 409.

8.4.5. DELETE /subscriptions/{subscription_id}

Назначение: архивирование подписки.
Доступ: защищенный.
Параметр пути: subscription_id — UUID.
Тело: отсутствует.

Успешный ответ: 204 No Content. Устанавливается is_archived=true. Записи Payment не удаляются. Повторный запрос для уже архивированной подписки также возвращает 204. Физическое удаление Subscription через этот endpoint не выполняется.

8.4.6. POST /subscriptions/{subscription_id}/restore

Назначение: восстановление архивной подписки.
Доступ: защищенный.
Тело: отсутствует.

Успешный ответ: 200 OK — полный объект подписки с is_archived=false. Если status=cancelled, запись остается cancelled. Восстановление не активирует отмененную подписку. Для active/paused сохраняется соответствующее состояние; для active пересчитывается ближайшая дата по правилам 7.3.1–7.3.3.

8.5.1. POST /payments

Назначение: регистрация фактического списания.

{
  "id": "payment-uuid",
  "status": "reversed",
  "reversed_at": "2026-11-20T12:00:00Z",

8.7. API аналитики

Общие правила: все endpoint-ы защищены; суммы возвращаются строками; все итоги разбиваются по currency; фактическая аналитика включает только succeeded операции; интервал дат локальный и полуоткрытый [date_from, date_to).

8.7.1. GET /analytics/summary

Назначение: сводная аналитика фактических расходов за период.
Query-параметры:
- date_from: обязательная дата YYYY-MM-DD;
- date_to: обязательная дата YYYY-MM-DD, исключающая правая граница;
- currency: необязательный ISO 4217 код.

Успешный ответ: 200 OK.
{
  "period": {
    "date_from": "2026-11-01",
    "date_to": "2026-12-01",
    "timezone": "Europe/Vilnius"
  },
  "totals_by_currency": [
    {
      "currency": "EUR",
      "gross_charges": "100.00",
      "refunds": "10.00",
      "net_expenses": "90.00",
      "charges_count": 4,
      "refunds_count": 1,
      "payments_count": 5
    }
  ]
}

payments_count равен сумме charges_count и refunds_count. При отсутствии операций по валюте группа не создается.

8.7.4. GET /analytics/upcoming

Назначение: прогноз ожидаемых расходов по активным подпискам.
Query-параметр:
- month: необязательный YYYY-MM; по умолчанию следующий календарный месяц относительно локальной даты пользователя. Разрешены текущий и будущие месяцы.

Успешный ответ: 200 OK.
{
  "month": "2026-12",
  "timezone": "Europe/Vilnius",
  "totals_by_currency": [
    {
      "currency": "EUR",
      "forecast_amount": "45.99",
      "categories": [
        {
          "category_id": "uuid",
          "category_name": "Entertainment",
          "forecast_amount": "45.99"
        }
      ]
    }
  ],
  "items": [
    {
      "subscription_id": "uuid",
      "service_name": "Netflix",
      "amount": "15.99",
      "currency": "EUR",
      "expected_payment_date": "2026-12-15",
      "category_id": "uuid",
      "category_name": "Entertainment",
      "billing_interval_unit": "month",
      "interval_count": 1
    }
  ]
}

items содержит отдельную запись для каждой ожидаемой даты платежа. Для подписки с несколькими платежами в месяце возвращается несколько элементов. totals_by_currency содержит сумму таких элементов; categories — детализацию по категориям. В прогноз не включаются paused, cancelled и archived подписки.

8.8. Ограничения доступа и журналирование API

1. Все endpoint-ы, не отмеченные как публичные, требуют действующий access token и проверку is_active пользователя.
2. Если подтверждение email обязательно, все защищенные бизнес-endpoint-ы также требуют is_verified=true. Endpoint-ы подтверждения и повторной отправки токена остаются публичными.
3. Любое изменение финансовой записи, подписки, категории, email, пароля или сессии создает AuditLog в той же транзакции, что и бизнес-изменение.
4. request_id создается для каждого входящего запроса, возвращается в error.request_id и записывается в логи и AuditLog при наличии бизнес-события.
5. В логи запрещено записывать пароли, access token, refresh token, содержимое auth-cookie, CSRF token и другие секреты.
6. Ответы endpoint-ов не должны содержать hashed_password, refresh_token_hash, request_hash и иные внутренние хеши или секреты.

8.9. Критерии приемки API-контрактов

1. Для каждого endpoint-а реализованы описанные HTTP-метод, путь, схема запроса, схема успешного ответа и коды ошибок.
2. Все денежные значения в JSON являются строками и обрабатываются без float.
3. Все списки имеют пагинацию и ограничение limit не более 100.
4. Все проверки принадлежности данных выполняются на backend-уровне и подтверждены негативными API-тестами.
5. Все три endpoint-а создания с обязательным Idempotency-Key подтверждены тестами повторного и конкурентного запроса.
6. Создание возврата подтверждено тестами частичного, полного, превышающего лимит и конкурентного возврата.
7. Расчет периодичности подтвержден тестами конца месяца, високосного года, нескольких интервалов за месяц и ручного изменения next_payment_date.
8. Аналитика подтверждена тестами нескольких валют, локальных границ месяца, возврата в другом месяце и месяцев без операций.
9. Прогноз подтвержден тестами active/paused/cancelled/archived, еженедельной периодичности и нескольких списаний в одном месяце.
10. Любая ошибка возвращает единый формат error, а успешная операция с кодом 204 не содержит тела ответа.
11. Для обязательного Idempotency-Key проверены отсутствие заголовка, недопустимая длина и ожидание конкурентной транзакции с последующим возвратом сохраненного результата.
12. Для подписок проверены чтение архивной записи, запрет PATCH до восстановления и регистрация платежа по paused-подписке без смены статуса.
13. Для смены email проверены резервация pending_email, запрет параллельной регистрации зарезервированного адреса и очистка резервации после подтверждения или истечения срока.
14. Для monthly проверены одинаковые месячные последовательности во всех валютах и частичные первый/последний месяцы на границах произвольного периода.
